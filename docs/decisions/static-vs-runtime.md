# 决策：构建时静态提取 vs 运行时反射

文档站的属性表、事件、插槽、类型必须**可复现、可审计、与发布版本绑定**。我们对比两种路径：

| 维度 | 构建时静态提取（采纳） | 运行时反射（不采纳为主路径） |
|---|---|---|
| 版本一致性 | 从指定提交 `git show <sha>:file` 读取，天然不可变 | 反射当前安装/运行的组件，分支更新后旧文档可能读到最新代码 |
| 副作用安全 | 不执行组件代码，无渲染副作用 | 必须实际 import/挂载组件，可能触发网络、定时器、全局污染 |
| 可在 CI 门控 | 提取 + 示例测试同一次构建产出契约 | 依赖运行环境（浏览器/框架版本），结果漂移 |
| 表达力 | 仅限源码可证明的信息 | 可拿到真实 props 默认值、校验器、运行时枚举 |
| 无法推断的字段 | 显式标记 `inferred:false`，要求 `*.manual.json` 人工补证 | 同样无法得到“图标允许哪些名字”等跨包事实 |
| 失败爆炸半径 | 解析失败只阻断该版本构建 | 反射崩溃可能影响构建进程甚至站点 |

## 结论

* **唯一事实源是构建时静态提取**（`tools/extract.mjs`）。属性表、事件、插槽、类型与交互示例必须来自同一 `buildId`。
* 运行时反射仅用于**示例运行器**（`tools/harness.mjs` + 预览沙箱）去验证组件可交互性，结果作为测试产物落库；它不产生文档契约。
* 静态无法证明的字段（自由 VNode、外部图标注册表、消费者决定的插槽内容）在源码打 `@manual` 标记，由 `<component>.manual.json` 提供 `description/values/reason`。若标记存在但缺人工证据，构建硬门控失败（`manualEvidenceComplete=false` → build rejected）。
* 每个版本页只渲染 `component_versions.commit_sha` 对应构建的产物；发布后行不可变。分支更新只影响之后的新构建，无法回灌旧文档。

## 递归类型别名

类型别名单独解析并做引用图分析（`resolveAlias`，深度上限 50 + 已访问集合），
`RichNode`（直接自引用）、`ClickTrace`（字段自引用）都被标记为 `recursive`，避免无限展开；非递归的 `ButtonSize`/`Variant` 正常给出引用链。
